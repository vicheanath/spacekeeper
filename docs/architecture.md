# Architecture

## The shape of the thing


Two crates and an app. That is the whole thing.

## Why it is not layered further

An earlier draft split the core into `domain` / `application` / `infrastructure`
crates with ports and adapters. That was dropped deliberately.

SpaceKeeper has exactly one consumer (the desktop app), one storage backend
(SQLite), and no plans for either to change. Ports-and-adapters buys the ability
to swap implementations behind interfaces — a cost paid on every single change,
for a benefit this project would never collect. What is left is ordinary Rust:
modules with clear responsibilities, dependencies pointing one way, and no
indirection that does not earn its place.

The extensibility the project genuinely needs — adding scanners — is served by
one trait and a registry, which costs nothing.

## The one abstraction: `Scanner`

```rust
#[async_trait]
pub trait Scanner: Send + Sync {
    fn metadata(&self) -> ScannerMetadata;
    fn is_available(&self, context: &ScanContext) -> bool { /* platform check */ }
    async fn scan(&self, context: &ScanContext) -> Result<Vec<ScanResult>>;
}
```

`ScannerRegistry` is the only thing that knows which concrete scanners exist,
and it is populated by the application at startup. Adding a scanner therefore
touches no existing code. Registering an id that already exists replaces it,
which is how a plugin overrides a built-in.

The context is borrowed rather than owned (the original sketch had
`scan(self, context: ScanContext)`) because every scanner in a run shares one
context; cloning it per scanner would duplicate roots and options for nothing.

### Declarative scanners

Most scanners are "look in this well-known folder". Writing thirty near-identical
`impl Scanner` blocks for those would be thirty places for a safety bug to hide,
so they are *data* instead:

```rust
PathRule {
    id: "xcode_derived_data",
    name: "Xcode DerivedData",
    explanation: "Build artifacts generated by Xcode. Safe to remove — Xcode \
                  recreates them the next time you build, which takes longer \
                  that one time.",
    category: Category::BuildArtifact,
    risk: RiskLevel::Safe,
    paths: &["~/Library/Developer/Xcode/DerivedData"],
    platforms: &["macos"],
    // …
}
```

One `RuleScanner` runs all of them. Traversal, measurement, cancellation, size
filtering and guard enforcement are written once and are identical for every
rule — including rules a third party adds. Supporting Unity, Steam or Adobe is a
new row in [`catalog.rs`](../crates/spacekeeper-scanners/src/catalog.rs), not new
code.

Bespoke `impl Scanner` types are for the cases with real logic: duplicate
detection, dating a project by its manifest, querying the Docker daemon.

## Safety: propose vs. decide

This is the central design decision, and everything else follows from it.

A scanner **proposes** a risk level. It does not decide anything. The engine
applies [`recommend::apply_policy`](../crates/spacekeeper-core/src/recommend.rs)
to *every* result, whatever produced it:

```rust
pub fn apply_policy(result: &mut ScanResult, guard: &PathGuard) {
    if guard.check(&result.path).is_err() {
        result.risk = result.risk.max(RiskLevel::Dangerous);  // only ever raises
        result.deletable = false;
    }
    if result.risk == RiskLevel::Dangerous {
        result.deletable = false;
    }
}
```

`RiskLevel` derives `Ord` specifically so this can use `max` — risk is a lattice
that only moves one way. A scanner claiming `~/.ssh` is `Safe` gets overruled,
and that behaviour is asserted in a test named
`policy_forces_protected_paths_to_dangerous_and_undeletable`.

The guard runs **again** inside `CleanupEngine::execute`, because a scan may be
minutes old by the time a user clicks. Re-validating at the moment of deletion
means a stale report cannot be a vulnerability.

### Three tiers, not a boolean

An earlier version of the guard returned `bool`. That forced a bad trade:
refuse `~/Documents` outright and the size explorer is useless exactly where
users have the most to reclaim; allow it and one scanner bug eats a thesis.

`Protection` has three states instead:

| Tier | Examples | Automated cleanup | Explorer |
|---|---|---|---|
| `Refused` | `/etc`, `~/.ssh`, `~/.config`, `/Volumes/X`, `Thing.app`, home itself | never | never |
| `Caution` | `~/Documents`, `~/Pictures`, iCloud Drive, `.git` | never | yes, after an explicit acknowledgement |
| `Allowed` | everything else | yes | yes |

Widening is possible in exactly one place — `CleanupRequest::authority` — and it
widens by exactly one tier. It defaults to `Automated`, including when
deserialised from a payload that omits it, so forgetting to set it can only
ever fail safe.

Each tier also carries a *reason* in plain language ("the keys you use to sign
in to other machines"), which is what the UI shows. The settings screen renders
the same list the guard enforces, so the screen cannot drift from the behaviour.

### What the guard refuses outright

| Rule | Why |
|---|---|
| Inside a refused tree (`~/.ssh`, `/etc`, `C:\Windows`) | irreplaceable or system-critical |
| *Contains* a protected tree (deleting `/home` to reach a cache) | ancestor check, not just descendant |
| The home directory itself | protected exactly, not as a subtree — almost everything we clean lives inside it |
| Fewer than two path components (`/`, `/usr`) | nothing legitimate is that shallow |
| A volume root (`/Volumes/Backup`, `/media/usb`) | that is a whole disk, not a folder on one |
| An application bundle (`*.app`, `*.framework`, `*.kext`) | installed software |
| Relative, or containing `..` | would defeat every prefix check above |
| User-added ignore list | the user's decision outranks ours |

## Not counting the same bytes twice

Two scanners can legitimately find the same disk space. `app_cache` sweeps
`~/Library/Caches`; `chrome_cache` reports a folder inside it. Both findings are
true, and summing them told the user they could reclaim more space than exists —
in the worst case inflating the one number the whole dashboard is built on.

`recommend::dedupe_overlapping` runs before ranking and collapses two shapes:

* **the same path from two scanners** — the higher-confidence one wins, so the
  scanner written specifically for Chrome beats the generic sweep and the user
  reads the better explanation;
* **a path inside another** — the descendant is dropped, since deleting the
  ancestor removes it anyway. An ancestor only covers its children if it is
  itself deletable; when the parent is protected the child is the only
  actionable item and has to survive.

That is the safety net. The catalogue also avoids the overlap in the first
place: a sweep declares an `exclude` list naming the folders that specific
scanners own, and three tests fail the build if a new rule reintroduces an
overlap — one for identical paths, one for a rule nested inside another, and
one that checks every wildcard sweep cedes what it should. Those tests found
three real cases when they were added, including crash reports being silently
swallowed by the generic log sweep.

The broad sweeps also report **per application** rather than as one blob, so
`~/Library/Caches` becomes "Xcode 12 GB, Slack 800 MB, …" and a user can clear
one and keep another. Reverse-DNS folder names (`com.google.Chrome`) are
rendered as something recognisable.

## Cancellation and pause

A scan touches millions of paths across a Rayon pool, blocking `walkdir`
iterators, and async scanners that shell out. Rather than two mechanisms,
[`Control`](../crates/spacekeeper-core/src/control.rs) is one cheap handle that
works from both worlds: synchronous workers park on a condvar (`check()`), async
tasks poll (`check_async()`). Checks are amortised — once every 256 directory
entries — because an uncontended mutex per entry does show up at ten million
files.

Cancellation is one-way, and each scan gets a fresh handle. A stale "stop" from
a previous run therefore cannot cancel the current one.

A cancelled scan still returns everything found so far. Throwing away thirty
seconds of work because someone pressed stop would be hostile.

## Failure isolation

One broken scanner must not cost the user the other twenty results. `ScanEngine::run`
never returns `Err`:

- a scanner returning `Err` → recorded as `Failed`, scan continues;
- a scanner that *panics* → caught at the `JoinSet` boundary, recorded, scan continues;
- a scanner reporting `Error::ScannerUnavailable` (Docker installed but not
  running) → recorded as **`Skipped`**, not failed. A laptop without Docker
  should show nothing, not a red error.

Every outcome lands in `ScanReport::scanners`, so a scan that quietly found
nothing is distinguishable from one that quietly broke.

## Concurrency

Scanners run concurrently under a semaphore sized `min(cpu × 2, 16)`. They are
I/O bound, so oversubscribing cores helps — but running all thirty at once on a
spinning disk turns sequential reads into thrash.

Inside a scanner, directory measurement fans out over Rayon
(`fsutil::measure_all`). Sizing twelve candidate cache folders concurrently is
close to a free twelve-fold speedup on an SSD, since the work is almost entirely
I/O latency.

Blocking filesystem work always goes through `spawn_blocking`; nothing blocks a
Tokio worker.

## Frontend state

The split is deliberate:

- **TanStack Query** owns anything the backend is the source of truth for:
  reports, history, settings, disks. Nothing auto-refetches — there is no
  network latency to hide and a scan is expensive — so the UI invalidates
  explicitly when it knows something changed.
- **Zustand** owns genuinely local state: the selection, live scan progress,
  the theme.

Progress events are fire-and-forget on an unbounded channel; a send failure is
ignored, because a scan that stalls when a window stops draining events would be
worse than a lost progress tick. The number of *completed* scanners is
deliberately not sent — the UI counts terminal events itself, so the bar cannot
jump backwards when concurrent scanners interleave.

## The size explorer

`browse.rs` walks a directory and measures every child. It exists because no
catalogue of known paths will ever find the 40 GB of raw video in someone's
project folder.

Two things make it fast enough to click through: children are measured in
parallel on Rayon, and results are memoised in a `SizeCache`, so stepping back
up a level — most of what browsing *is* — is instant. The cache is invalidated
for a path and its ancestors after a deletion, since those are the totals that
changed.

Deletion from the explorer is path-addressed, which would otherwise let the
webview name any path. `AppState` therefore remembers the paths from the most
recent listing and `delete_browsed` refuses anything else — the same "backend is
the source of truth" property the scan flow gets from result ids. See
[explorer.md](explorer.md).

## Where things deliberately stop

**Docker** is reported but never deleted. Its images and volumes are not plain
files, removal is not reversible, and deleting a volume can destroy a database
someone needs. SpaceKeeper reports the usage and prints the exact `docker …`
command. The results are marked `deletable: false`, so the cleanup engine would
refuse them even if the UI asked.

**Undo** is offered only where the platform can deliver it. Linux and Windows
expose a trash-restore API; macOS does not, so the app says "open the Trash and
choose Put Back" instead of showing a button that fails.
